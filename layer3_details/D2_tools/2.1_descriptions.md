# 2.1 · Tool descriptions

📍 **Map:** Whole picture → 2. Tools → **2.1 Descriptions**  ·  ⏱ 3 min

## The one rule
> The description is **how Claude chooses a tool**. A bad description means a bad choice.

## Picture it
A new employee in front of buttons labelled "Retrieves customer information" and "Retrieves order details". Which one for *"check my order #12345"*? They guess.

## Know these 🎯
- A good description has: **what it does, input formats, example queries, edge cases, when to use it vs similar tools.**
- Overlapping tools (`analyze_content` vs `analyze_document`) get mixed up. Fixes:
  - **Rename + re-describe** (`analyze_content` → `extract_web_results`).
  - **Split** a generic tool into specific ones (`extract_data_points`, `summarize_content`, `verify_claim_against_source`).
- The **system prompt** can steer tool choice by accident. Check it for keyword-sensitive instructions.

## ⚠️ Exam traps (this is sample question #2)
| ❌ Wrong | ✅ Right ("first step") |
|---|---|
| Few-shot examples of routing | Expand the descriptions |
| A keyword routing layer | Over-engineered |
| Merge both into one tool | Valid, but too much work for a *first* step |
| Force it with `tool_choice` | Fix the description |
