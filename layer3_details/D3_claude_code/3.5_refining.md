# 3.5 · Iterative refinement

📍 **Map:** Whole picture → 3. Claude Code → **3.5 Refining**  ·  ⏱ 3 min

## The one rule
> Give Claude **something concrete to check against**: examples or tests. Not a vague description.

## Picture it
"Make the discount work." "Done!" Is it? A test that passes is proof. Words aren't.

## Know these 🎯
- Prose gets misread? → give **2–3 concrete input → output examples**.
- **Test-driven:** write tests first (behavior, edge cases, performance) → share the **failures** → iterate.
- **Interview pattern:** in an unfamiliar area (cache invalidation, failure modes), Claude **asks you questions first**, then builds.
- Edge case broken (e.g. null values in a migration script) → give **that specific test case** with input + expected output.
- **Problems that affect each other → one detailed message.** Independent problems → fix **one by one**.

## 👀 What it looks like
❌ Prose: *"Normalize the phone numbers properly."*

✅ Concrete examples:
```
"(555) 123-4567"     → "+15551234567"
"555.123.4567 ext 9" → "+15551234567;ext=9"
""  / null           → null
```
✅ Interview pattern:
```
You: Before writing any code, ask me questions about cache invalidation
     and failure modes for this service. Then propose a design.
```
**Piece by piece**
- 2–3 **input → output** pairs remove the guessing.
- Include the **edge case** (empty/null), since that's where code breaks.
- The interview pattern surfaces things **you** hadn't thought about.

## ⚠️ Exam traps
| ❌ Wrong | ✅ Right |
|---|---|
| Re-explain in longer prose | 2–3 input/output examples |
| Fix 3 interacting bugs one by one | All in one message |
| Fix 3 unrelated bugs in one message | One by one |
