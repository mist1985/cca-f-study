2.2 Error messages

📍 Map: Whole picture → 2. Tools → 2.2 Errors · ⏱ 3 min

The one rule

An error must say what broke and whether a retry helps. And empty ≠ failed.

Picture it

"Operation failed." Retry? Tell the customer? Give up? Claude can't know.
"Stock system busy, retry in 60 s" → now it knows.

Know these 🎯

  • MCP flag: isError: true tells Claude "this is a failure".
  • 4 kinds of error:
    • transient: timeout, service down → retry
    • validation: bad input → fix the input
    • business: policy says no → don't retry, explain kindly
    • permission: not allowed
  • Return: errorCategory + isRetryable + a readable message.
  • Business rule broken → retryable: false + a customer-friendly explanation.
  • Access failure (couldn't look) ≠ valid empty result (looked, found nothing).
  • Helpers fix temporary errors themselves and pass up only what they can't fix, with what they tried + partial results.

👀 What it looks like

The tool result Claude receives:

{"isError": true,
 "content": [{"type": "text", "text": "...the error details below, as text..."}]}

The error details (your own structure inside the text):

{"errorCategory": "transient",
 "isRetryable": true,
 "message": "Inventory service timed out after 10s. Retry once in ~30s."}

A business-rule error:

{"errorCategory": "business",
 "isRetryable": false,
 "message": "Refund exceeds the $200 self-service limit. Tell the customer a manager will review it."}

A valid empty result (not an error):

{"isError": false,
 "content": [{"type": "text", "text": "No orders found for C-1029 in the last 90 days."}]}

Piece by piece

  • isError: true = failure. isError: false + "no orders" = a successful search with zero results.
  • errorCategory + isRetryable let Claude choose: retry, fix the input, or explain.
  • The business message is customer-friendly, so Claude can pass it on.
