2.2 Error messages

📍 Map: Whole picture → 2. Tools → 2.2 Errors · ⏱ 3 min

The one rule

An error must say what broke and whether a retry helps. And empty ≠ failed.

Picture it

"Operation failed." Retry? Tell the customer? Give up? Claude can't know.
"Stock system busy, retry in 60 s" → now it knows.

Know these 🎯

  • MCP flag: isError: true tells Claude "this is a failure".
  • 4 kinds of error:
    • transient: timeout, service down → retry
    • validation: bad input → fix the input
    • business: policy says no → don't retry, explain kindly
    • permission: not allowed
  • Return: errorCategory + isRetryable + a readable message.
  • Business rule broken → retryable: false + a customer-friendly explanation.
  • Access failure (couldn't look) ≠ valid empty result (looked, found nothing).
  • Helpers fix temporary errors themselves and pass up only what they can't fix, with what they tried + partial results.

⚠️ Exam traps

❌ Wrong✅ Right
Same "Operation failed" for everythingCategory + retryable + message
Timeout → return empty listThat's an error, not "no results"
Every tiny error goes up to the leadRetry locally first
🧠 Say it out loud: why is returning [] on a timeout dangerous?

Claude reads it as "nothing exists" and gives a confident wrong answer.
