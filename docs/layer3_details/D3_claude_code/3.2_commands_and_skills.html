3.2 Slash commands & skills

📍 Map: Whole picture → 3. Claude Code → 3.2 Commands & skills · ⏱ 3 min

The one rule

Always true → CLAUDE.md (always loaded). Specific task → skill or command (loaded on demand).

Picture it

A 40-step release process isn't pinned to the desk every day. It's a binder on the shelf, opened when you type /release.

Know these 🎯

WhereWho gets it
.claude/commands/✅ team (in git)
~/.claude/commands/❌ only you
.claude/skills/<name>/SKILL.md✅ team
~/.claude/skills/❌ only you. Personal variant? Use a different name

SKILL.md frontmatter (settings at the top):

  • context: fork → runs in an isolated helper. Verbose output (codebase analysis, brainstorming) doesn't pollute your main chat.
  • allowed-tools → limits tools while the skill runs (exam example: only file-write tools, to prevent destructive actions).
  • argument-hint → reminds the developer which argument to type.

👀 What it looks like

.claude/commands/review.md → team command /review:

Review the current diff against our checklist:
1. Security: injection, secrets, auth checks
2. Error handling on every external call
Report only real issues with file:line.

.claude/skills/codebase-map/SKILL.md:

---
name: codebase-map
description: Maps an unfamiliar module: entry points, data flow, dependencies.
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: [module-path]
---
Map the module at $ARGUMENTS and return a one-page summary.

Piece by piece

  • context: fork → the noisy mapping runs in a separate subagent. Only the summary comes back.
  • allowed-tools → limited to read-only tools while it runs.
  • argument-hint → shows [module-path] so the developer knows what to type.

⚠️ Real-world vs exam

Current docs say allowed-tools only pre-approves tools and other tools still ask. The exam guide treats it as restricting tools. On the exam, go with the guide.

🧠 Say it out loud: a skill dumps 500 lines of analysis into your chat. Fix?

Add context: fork so it runs in an isolated helper.
